# Нагрузочное тестирование model-service

## Ожидаемое поведение и целевые показатели

Для приведённого ниже прогона заранее зафиксированы: 25 одновременных пользователей в течение 60 с,
скорость подключения — 10 пользователей в секунду, пауза между запросами каждого
пользователя — случайная от 0,1 до 0,3 с. При таком профиле ожидается не менее
50 запросов/с, доля ошибок менее 1% и p95 времени ответа не более 500 мс.
Успешным считается только HTTP 200 с массивом `models` в JSON. Это учебные цели,
а не заявленные показатели production-системы.

Сценарий: `GET /api/v1/projects/stress-test/models?offset=0&limit=20` с JWT
администратора через Nginx. Запросы распределяются между тремя экземплярами
model-service с весами 2:1:1. Проект `stress-test` выбран как пустая выборка;
тест не создаёт и не изменяет данные. При пустом списке модели не загружаются
и вызов inference-service за статусами развёртываний не выполняется.

## Запуск

Нужны работающие Nginx, три экземпляра model-service, PostgreSQL и user-service
для JWKS. Locust 2.32.10 запускается в контейнере. Он один раз авторизуется
перед началом теста с `BOOTSTRAP_ADMIN_LOGIN` и `BOOTSTRAP_ADMIN_PASSWORD`
из `infra/.env` и использует полученный токен для запросов к model-service.
Master и workers совместно используют кэш `stress-test/docker-results/.login-cache.json`.
Через пять минут результат login обновляется, в том числе во время долгого теста.
`make locust` создаёт начального администратора, если его ещё нет.

Параметры теста задаются в `stress-test/.env`. Сценарий отправляет запросы
`GET /api/v1/projects/{project}/deployments` для чтения активных развёртываний.
Этот запрос обращается через gRPC к inference-service, поэтому результаты
включают время этой зависимости. Авторизация в измерения не входит.

Файл `.env` исключён из Git. Если его нет, создайте его из
`stress-test/.env.example`. Запустите из корня проекта:

```sh
make locust
```

Команда запускает PostgreSQL, применяет миграции, создаёт администратора,
поднимает сервисы, Locust UI и два worker-процесса. Число workers можно
изменить, например `make locust LOCUST_WORKERS=6`. Если `stress-test/.env` отсутствует, команда
создаёт его из примера. Для bootstrap администратора необходим Go; если
администратор уже существует, его пароль не обновляется автоматически.

Откройте `http://localhost:8089`, укажите количество пользователей и скорость
их подключения, затем нажмите **Start swarming**. Адрес `http://nginx:80`
доступен внутри Docker-сети и уже задан в форме. Чтобы остановить интерфейс:

```sh
docker compose --env-file infra/.env --env-file stress-test/.env \
  -f stress-test/docker-compose.yaml stop locust-ui locust-worker
```

Контейнер подключается к сети `inference-platform_default` и отправляет запросы
на `http://nginx:80`; для другой сети измените `MODEL_TEST_NETWORK` в `.env`. Результаты
записываются в `stress-test/docker-results/` и перезаписываются при следующем
запуске. Токен должен оставаться действительным в течение теста. Новый сценарий
чтения развёртываний и путь через внутреннюю сеть Docker отличаются от сценария и
сетевого пути приведённого ниже прогона; результаты напрямую не сопоставимы.

## Конфигурация и результаты

Тест выполнен 9 ноября 2026 года на локальной машине macOS ARM64. Locust
2.32.10 работал на хосте под Python 3.13.7. Nginx, три экземпляра
model-service, PostgreSQL и user-service работали в Docker Desktop; Docker
28.4.0 сообщал о 8 CPU и примерно 3,83 ГиБ памяти. Нагрузка генератора и
сервисов использовала одну физическую машину. Все три экземпляра подключались
к одной PostgreSQL, без реплик базы данных.

Параметры запуска соответствовали профилю выше: 25 пользователей, набор по
10 пользователей/с, ограничение запуска 60 с, задержка 0,1–0,3 с. Токен
получен заранее; его получение не входит в измерения. В выбранном проекте перед
тестом было 0 моделей. Фактически Locust сообщил о наборе всех пользователей
примерно за 2 с, а интервал между отметками начала и завершения в его журнале
составил около 56,8 с.

## Выводы

Все три заданных порога выполнены для проверенного профиля и пустой выборки.
Один прогон не показывает предельную пропускную способность системы: сценарий
ограничен числом пользователей и паузами, а генератор и сервисы конкурируют
за ресурсы одной машины. Результаты нельзя переносить на непустые проекты:
для них обработчик дополнительно получает статусы развёртываний через
inference-service. Тест не измеряет операции записи, поведение при отказе,
длительную стабильность или масштабирование PostgreSQL.
