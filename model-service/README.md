# Model Service: спецификация реализации

Статус: проектирование. Этот документ описывает целевое поведение, а не утверждает, что оно уже реализовано. Задачи и критерии приёмки: [tasks/model-service.md](tasks/model-service.md).

## Назначение и границы

ModelService хранит принадлежащую проекту модель — именованную конфигурацию запуска, созданную пользователем. Создание модели не создаёт контейнер. Запуск создаёт deployment в InferenceService; остановка запрашивает остановку последнего deployment. Историю и фактическое состояние deployment хранит InferenceService. Proxy уже существует и в эту работу не входит.

Внутри БД модель имеет UUID; внешний проект идентифицируется неизменяемым `project_name`. Имя модели уникально в проекте: `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`, до 63 символов. Имя deployment используется в DNS-адресе без преобразования. Поля: `id`, `project`, `name`, `description`, `created_at`, `updated_at`, `spec`. Поле `username` при создании заполняется логином пользователя из claim `username` подписанного JWT. Удаление аккаунта не удаляет модели; межсервисный FK не создавать.

Первый и единственный поддерживаемый provider — `HUGGING_FACE`. Доступный сегодня Deployment API параметр — `spec.provider_hugging_face.repo`; остальные параметры не выдумываются. Пример создания:

```json
{
  "name": "qwen-small",
  "description": "Небольшая модель",
  "spec": {
    "provider_type": "HUGGING_FACE",
    "provider_hugging_face": {"repo": "Qwen/Qwen2.5-0.5B-Instruct-GGUF:Q4_K_M"}
  }
}
```

Проверять непустой ограниченный по длине `repo`, корректный provider и совпадение provider с вложенным объектом; отвергать неизвестные поля, `null` и неподдерживаемые provider. Не делать сетевой запрос к Hugging Face при создании. Приватные токены и секреты в `spec`, логах и ответах запрещены. В домене — типизированная спецификация, а не произвольный JSON; JSONB допустим как формат хранения с версией схемы и явной валидацией при чтении. Снимок спецификации каждого запуска принадлежит deployment и не меняется при последующем редактировании модели.

## Состояние и жизненный цикл

Статус модели вычисляется из **последнего созданного deployment** этой модели, а не из записи ModelService и не из последнего изменённого deployment. Порядок определяется `(created_at, deployment_id)` с уникальным tie-breaker; источник истины — InferenceService. Принимаемая модельная проекция:

| Последний deployment | Статус модели | Детали |
| --- | --- | --- |
| отсутствует, `STOPPED`, `FAILED` | `NOT_RUNNING` | При `FAILED` отдельно вернуть безопасный `deployment_status`, не теряя причину сбоя. |
| `PENDING`, `STARTING` | `STARTING` | Операция асинхронна. |
| `STARTED`, `RUNNING` | `RUNNING` | `STARTED` сейчас означает запущенный контейнер, **не** готовность модели отвечать на inference. |
| `STOPPING` | `STOPPING` | Повторный stop идемпотентен. |
| `UNKNOWN`, `UNSPECIFIED`, неизвестное enum-значение | `null` | `status_reason=UNKNOWN_DEPLOYMENT_STATUS`; нельзя выдавать `NOT_RUNNING`. |

Ответ модели включает `status`, `status_reason` и `latest_deployment` (`id`, исходный статус; `null`, если deployment никогда не существовал). Это позволяет оставить четыре бизнес-статуса, не маскируя ошибки неопределённым значением. Если InferenceService недоступен, GET возвращает `503`, timeout — `504`; не подставлять `NOT_RUNNING` и не использовать устаревший статус как актуальный. Список также возвращает ошибку целиком; не допускать N+1 запросов.

Start читает актуальную модель и отправляет `project`, `model_id`, идентификатор инициатора, `deployment_name` и снимок `spec`. Успешный ответ — `202 Accepted` с фактическим deployment ID и проекцией фактически возвращённого статуса, не фиктивный `RUNNING`. Допускается только один активный deployment для `(project, model_id)` и `(project, deployment_name)`; финальные `STOPPED`/`FAILED` разрешают новый запуск. Stop передаёт ID последнего deployment; после принятия — `202`, текущий статус затем читается из InferenceService. При отсутствии deployment или уже остановленном состоянии — идемпотентный `204`; `FAILED` также не требует stop. Stop чужого проекта запрещён.

Конкурентные start/stop, таймауты после отправки и повтор клиента нельзя решать проверкой перед RPC: решение об уникальности и атомарности — у владельца deployment. Добавить идемпотентный `request_id`/ключ операции в Deployment API и устойчивую дедупликацию с сохранением результата; тот же ключ с другим содержимым — конфликт. При неоднозначном ответе retry с тем же ключом не создаёт второй контейнер. Не держать транзакцию ModelService открытой во время RPC. Пока контракт не предоставляет этих гарантий, сценарий нельзя объявлять production-ready.

Текущий gRPC API не фильтрует историю по проекту или model ID; ModelService читает все страницы истории в порядке от новых запусков к старым. Для записей до миграции время создания неизвестно. В InferenceService требуется добавить `GetLatestDeployment(project, model_id)` и пакетное получение последних deployment по списку model ID в рамках одного проекта. Пакетный ответ различает отсутствие deployment и ошибку, соблюдает лимит размера страницы и изоляцию проектов. Индексировать выборку; реализовать защиту от гонок и идемпотентность на стороне InferenceService. Не использовать `GetDeploymentByName`: оно не задаёт проект и не определяет последнюю попытку.

## API и изменения модели

Базовый путь `/api/v1/projects/{project}/models`. Все методы получают project name из пути и работают только внутри него. Сохранить CRUD маршруты. Для запуска и остановки использовать вложенный ресурс deployment существующей модели:

| HTTP-операция | Поведение |
| --- | --- |
| `POST /{model_id}/deployment` | Запустить существующую модель: вызвать `StartDeployment` InferenceService и вернуть `202` с ID и текущим состоянием. |
| `GET /{model_id}/deployment` | Получить последний deployment модели из InferenceService; если истории нет — `404`. |
| `DELETE /{model_id}/deployment` | Остановить последний deployment через `StopDeployment`; это не удаляет модель и историю. При принятой остановке — `202`, при уже остановленном или отсутствующем deployment — `204`. |

`POST` не создаёт модель и использует её сохранённую spec. Он требует заголовок
`Idempotency-Key`: повтор с тем же ключом возвращает сохранённый результат,
а новая попытка после остановки требует нового ключа. Результат сохраняется
в PostgreSQL; правила обработки повторов описаны в [README проекта](../README.md).
`GET /api/v1/projects/{project}/deployments/history` возвращает историю запусков,
включая остановленные и завершившиеся ошибкой. Каждый элемент содержит `id`,
`model_id`, `project`, `status`, `name`, `username`, `started_at` и `updated_at`.
Список моделей включает статус по последнему deployment и поддерживает пагинацию.

Редактирование description допускается всегда. Изменение имени или spec — только когда подтверждено отсутствие активного deployment; при недоступном InferenceService отклонять изменение. Поскольку предварительная проверка не исключает гонку с start, сериализацию и версионирование необходимо реализовать на стороне orchestration с устойчивым механизмом согласования между сервисами; нельзя обещать атомарность одной проверкой. Удаление — только при подтверждённом отсутствии активного deployment; запись истории deployment сохраняется, а внешние ресурсы не удаляются косвенно. Эти ограничения обязательны и при одновременных запросах. Версии существующих записей и миграция локальной БД должны быть описаны без потери данных.

## Авторизация

Каждый публичный маршрут требует Bearer access JWT UserService: проверка RS256, `typ`, `kid`, подписи по доверенному настроенному JWKS, issuer, audience, времени, UUID, версии и известных claims; не загружать ключи по адресу из токена. JWKS загружается только с настроенного `USER_JWKS_URL`, с таймаутом, ограничением размера ответа и коротким кэшем. Невалидный или отсутствующий токен — `401`; недоступность доверенного JWKS при невозможности проверить подпись — `503`, fail closed. Не логировать JWT.

| Действие | Нужное разрешение на проект |
| --- | --- |
| Создать | `can_create_model` |
| Получить, список и статус | `can_read_model` |
| Изменить | `can_update_model` |
| Удалить | `can_delete_model` |
| Запустить | `can_start_model` |
| Остановить | `can_stop_model` |

`admin` имеет все права; `analyst` имеет глобальное чтение моделей, но не запись. Проектные права складываются с глобальными только при точном совпадении `project.name` в project-token с проектом пути. Обычному `user` для действий нужен подходящий project-token; глобальный user-token не даёт проектных разрешений. Проверки выполняются на границе и в application service через типизированный доверенный Actor; не принимать `username`, роль или права из тела, query либо клиентских заголовков. Проект и модель из разных проектов не раскрывать: `404` для недоступного ресурса; для известного проекта без разрешения действия — `403`. До доступа к ресурсу проверять права так, чтобы ответы не раскрывали существование чужой модели.

JWT — снимок прав, локальная проверка допускает задержку отзыва не более пяти минут, включая leeway. При `auth_version` без онлайн-проверки мгновенного отзыва нет. Прямой gRPC InferenceService не должен обходить ModelService: в production ограничить сетевой доступ и аутентифицировать вызывающий сервис через mTLS/workload identity; до внедрения это явная граница безопасности. Пользовательский JWT в llama.cpp UI не передаётся. При несовместимости текущего поля `username` Deployment API заменить/версионировать контракт на достоверный actor ID; не записывать непроверенное имя из запроса.

## Эксплуатация

Конфиг: адреса и таймауты PostgreSQL, Inference gRPC и JWKS, issuer/audience, ограничение request body, graceful shutdown. Health — процесс; readiness — БД и обязательные зависимости по документированной политике. Таймаут RPC ограничен deadline запроса, ошибки downstream маппятся без утечки внутренних деталей. Логи и аудит содержат actor ID, действие, project, model/deployment ID и результат, но не токены и секреты; метрики не используют ID как labels. Использовать миграции и sqlc по аналогии с UserService, ограниченные подключения и запросы, проверку схемы до обработки запросов. Не применять миграции молча к существующему тому.

`GET /api/v1/projects/{project}/deployments` возвращает все активные запуски проекта в поле `deployments`: ожидающие и запускающиеся (`pending`, `starting`), а также запущенные (`running`). Формат элементов и требуемое право чтения совпадают с историей запусков. ModelService получает все страницы `ListDeployments` и фильтрует их по проекту.

Список моделей содержит `status` по последнему deployment: `starting` (включая ожидание), `running`, `stopping`, `stopped`, `failed` или `unknown`. Если запусков не было, возвращается `stopped`. При недоступности inference-service список не возвращается. Для определения последнего запуска требуется миграция `000007_deployment_created_at.sql`; порядок запусков, созданных до неё, восстановить невозможно.

Удаление модели разрешено, если её deployment отсутствуют либо находятся в состояниях `stopped` или `failed`. Если есть deployment в других состояниях, API возвращает 409. При недоступности inference-service удаление не выполняется. История запусков сохраняется.

В списках deployment `started_at` — время создания записи запуска; `updated_at` — время создания записи или последнего изменения статуса. Для старых записей без этих данных возвращается `null`.
